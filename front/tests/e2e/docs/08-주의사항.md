# 08. 주의사항 (반복 실수 차단)

정상 절차로 진행하면 화면이 깨지지 않고 마이그레이션이 실제로 동작해야 한다.
아래를 놓치면 **실패가 반복**되거나, 더 나쁘게는 **깨졌는데도 통과**한다.

## A. E2E 테스트 3분류 — 더미는 `@dummy` 로만

E2E 테스트는 성격에 따라 **세 종류**로 나눈다. 이 구분이 태그·프로젝트 구성에 그대로 드러나야 한다.

| 분류 | 태그 | 실서버 | 더미(mock·fixture 기본값) |
|------|------|:------:|:------------------------:|
| **더미(dummy)** | **`@dummy` 명시 필수** | 불필요 | **허용 — `@dummy` 일 때만** |
| **기능(function)** | `@unit` 등 | **필수** | **금지** |
| **시나리오(scenario)** | `@scenario`(+`@costly`) | **필수** | **금지** |

- **더미** — 실서버 없이 도는 검증(순수 UI 로직·셀렉터·라우팅·빈 상태 렌더링 등). 실 연계 프레임워크를 치지 않는다. **반드시 `@dummy` 로 그 사실을 드러낸다.**
- **기능** — 화면별 기능 검증. mock 없이 실제 연계 프레임워크를 쳐서 계약 파손을 잡는다.
- **시나리오** — 마이그레이션 전체 흐름. 실제 자원까지 만들어 end-to-end 로 검증한다.

### 규율

1. **`@dummy` 로 명시한 것만 더미를 쓴다.**
2. **기능·시나리오에 더미가 있으면 금지.** 더미가 섞이면 *실제로는 에러인데 정상처럼 보여* 결함을 감춘다.
3. 실패·빈 응답은 mock·더미·목업으로 덮지 않고 **실패로 그대로 드러낸다**(README 원칙 1 "폴백 금지"와 같은 취지).

### ⚠️ 실제 사고 (2026-07-15) — 더미가 결함을 가린 사례

시나리오 테스트를 `TEST_SOURCE_IP`·`TEST_SOURCE_PRIVATE_KEY` **미주입**으로 돌렸다.
그러면 `fixtures/test-data.ts` 의 기본값(`ip=''`, `password='e2e-dummy-pass'` — 소스 SSH가 가짜)으로 실행된다.
소스 수집이 가짜라 마이그레이션이 **"행 없음"으로 실패**했는데, 더미가 그 결함을 정상처럼 가렸다.

→ **기능·시나리오는 실서버 전제 필수값이 비면 fixture 기본값으로 진행하지 말고 즉시 실패시킨다.**
`BASE_URL`·`TEST_SOURCE_IP`·`TEST_SOURCE_PRIVATE_KEY` 등이 없으면 더미로 조용히 도는 대신 명시적으로 죽여, 사람이 "이건 실서버로 안 돌았다"를 바로 알게 한다.

## B. 에이전트별 주의사항

### B-1. cm-beetle — 인프라 이름 충돌

cm-beetle 은 타깃 인프라를 **타깃 모델에 적힌 이름(기본 `infra101`, 또는 `infra{n}`)** 으로 만든다.
같은 이름으로 재생성하면 충돌하고, **죽은 이전 인프라와 구분이 안 돼 "거짓 통과"** 가 난다
(노드가 죽은 `infra101` 을 보고 "EC2 생성 성공"으로 판정).

→ **워크플로우 툴에서 인프라 이름을 유니크하게 바꿔 전달**하고, 실행 전 **이전 인프라를 정리**한다.
이 저장소는 이미 그렇게 한다 — `features/scenarios/워크플로우툴-파라미터변경.feature`,
`features/scenarios/마이그레이션전체흐름.feature`, `steps/software.steps.ts`
(기본값 `infra101` 대신 바꾼 이름으로 워크로드가 생겼는지, **이번 실행이 만든 노드 id** 로 확인).

### B-2. cm-cicada — 워크플로우 이름 유일성 + request_body 방식

- **동일 이름 워크플로우 저장 불가** — cm-cicada 는 워크플로우 이름에 UNIQUE 제약이 있다.
  같은 이름으로 다시 저장하면 거부되고, 에러 모달이 남아 뒤 조작을 가린다.
  → `uniqueName()` / `RUN_ID` 접미사로 **유니크 이름**을 쓴다(`support/naming.ts`).
- **request_body 방식** — v0.5.1 에서 task 의 request_body 는 **참조 / 조합 / 리터럴** 폼을 가진다.
  방식별로 값이 어떻게 조립·보존되는지 주의한다(저장 시 `{}` 소실·참조 라운드트립 등).
  (배경: `cmig-workflow` → `notion/cm-bf-ep-전환워크플로우웹플래닝고도화/017_태스크본문전달방식현행화/`)

### B-3. ★ 추천 후보 선정 — 스펙·이미지가 모두 채워진 후보를 골라야 한다 (2026-07-15, 중요)

인프라 마이그레이션은 **스펙을 비롯한 모든 정보가 채워진 타겟**으로 등록해야 정상 동작한다.
그런데 **cm-beetle 추천 목록에는 일부 항목(스펙·이미지)이 비어(placeholder `"string"`) 추천되는 후보가 섞여 있다.**
빈 후보로 타겟 모델을 만들면 **저장은 되지만**(request_body 는 보존됨) beetle 이 **이미지를 못 풀어 인프라 생성이 실패**한다.

**실제 증거 (2026-07-15)** — 저장된 마이그레이션 워크플로우의 인프라 task `request_body` 에서
`targetInfra.name`·`connectionName` 은 채워졌으나 `nodeGroups[0].cspImageName="string"`, `imageId="string"` 로 비어 있었고,
그 결과 **MCI 가 생성되지 않았다**(비용 자원 0).

→ **목록 선정이 중요하다.**
- **E2E**: 추천 결과에서 `cspImageName`/`imageId` 등이 placeholder(`"string"`)·빈 값인 후보를 **거르고 완전 충전 후보를 고르도록 보정**한다.
  고를 후보가 없으면 **실패로 드러낸다**(더미로 채우지 않는다 — A 규율과 동일).
- **웹 사용자**: 빈(placeholder) 후보를 피하고 스펙·이미지가 채워진 후보를 고른다.

> "빈 결과를 오류로 착각"하는 문제와는 다르다. 여기서는 **후보가 채워진 것처럼 보이지만 스펙·이미지가 placeholder** 인 것이 핵심이다.

## C. 스크립트를 쓸 때 반복해서 틀리는 것 (2026-07-29, 통합 시나리오 검증에서)

아래는 전부 **한 번씩 실제로 틀렸던 것**이다. 새 스텝·Page Object 를 쓰기 전에 훑는다.

### C-1. ★ 폴백을 두지 않는다

`getByTestId('x').or(텍스트)` 처럼 대안을 두면, **식별자가 사라져도 테스트가 통과한다.** 화면이 깨진 바로 그 순간에 알려 주지 않으니 폴백은 안전장치가 아니라 눈가리개다.

→ 필요한 식별자가 화면에 없으면 **화면에 추가**한다(CLAUDE.md §12). 그리고 그 빌드로 돌린다. 아직 배포 안 된 식별자를 폴백으로 감싸 놓고 진행하지 않는다.

> **순서가 중요하다 (2026-07-29 실사고)** — 폴백을 먼저 지우고 식별자는 있다고 *가정*했다. `target-detail-custom-view` 는 소스 모델 상세에만 있고 타깃 모델 상세에는 없던 것이라, 타깃 모델을 편집하는 구간이 전부 클릭 타임아웃으로 죽고 그 뒤 구간이 연쇄로 무너졌다. **심고 → 빌드하고 → 그 빌드로 돌린 뒤에** 폴백을 지운다.
>
> `scripts/check-env.sh` 가 실행 전에 화면 소스를 뒤져 **필요한 식별자가 실제로 있는지** 확인한다. 없는 식별자를 기다린 타임아웃은 화면 탓인지 스크립트 탓인지 구분되지 않으므로, 시작 전에 막는다.

### C-2. 대상은 이름이 아니라 **식별자**로 잡는다

`awsb-infra101` 같은 이름은 접두어 + 타깃 모델 값이라 명명 규칙이 바뀌면 깨지고, **이전 실행이 남긴 동명 자원과 구분되지 않는다**(B-1 의 거짓 통과와 같은 뿌리).

→ 만든 직후 **실제 id 를 읽어 기록**하고 그것으로 찾는다(`support/handoff.ts`). 워크로드 목록 행은 `data-infra-id`·`data-infra-uid` 를 싣고 있다.

### C-3. 이름에 **날짜·시각**을 넣는다

고정 접두어는 같은 날 두 번째 실행에서 충돌한다. cm-beetle 은 같은 이름을 찾으면 **조용히 재사용**하므로 두 번째 실행이 첫 실행의 네트워크에 붙는다 — 실패조차 하지 않아 더 나쁘다.

→ `t{트랙}-{YYMMDD}-{HHMMSS}` (20자 이하 영숫자·하이픈). 이름만 봐도 언제 만든 것인지 읽힌다.

### C-4. 한 자리에서 붙잡고 기다리지 않는다

인프라가 만들어지는 동안 다른 트랙의 모델을 만들고, 소프트웨어가 깔리는 동안 다음 구간으로 넘어간다. **기다리는 일은 답이 필요한 자리에서** 한다.

- 고정 `waitForTimeout(120_000)` 같은 것을 두지 않는다 — **신호를 폴링**한다(예: DAG 등록 여부는 cm-cicada 실행 이력 조회가 응답하는지로 안다).
- 워크플로우 작업 상태는 *끝날 때까지* 기다리지 말고 **지금까지 실패한 것이 있는지**만 본다.

### C-5. 필드 이름은 계층마다 다르다 — 기억으로 쓰지 않는다

| 계층 | 포트 필드 |
| --- | --- |
| 소스 모델 `firewallTable` | `dstPorts` |
| 타깃 모델 `firewallRules` | `Ports` |
| cb-tumblebug 보안그룹 | **`Port`** |

틀린 이름으로 읽으면 전부 `undefined` 가 되어 **"포트가 안 열렸다"는 그럴듯한 오보**가 나온다. 실제로 정상 제품을 결함으로 보고할 뻔했다.

### C-6. 스텝은 자기가 갈 화면으로 **직접 이동**한다

구간별로 따로 실행하면 앞 단계가 화면을 물려주지 않는다. 목록을 열지 않고 행을 찾으면 *"행이 하나도 없다"* 는, 데이터가 없는 것처럼 들리는 에러가 난다. 실제로 다섯 번 걸렸다.

### C-7. 소스 서버 주소는 **사설 IP**

수집은 플랫폼 호스트에서 나가고, 소스 보안그룹은 그쪽으로만 SSH 를 연다. 공인 주소를 넣어도 **등록은 성공**하고 Collect Infra 만 조용히 비활성으로 남는다 — 실패가 몇 단계 뒤 "수집 결과 없음"으로 나타난다. 정본: `cmig-workflow/REMOTE-ENV-SETUP.md` §3.2

### C-8. 방화벽이 꺼진 소스는 규칙을 주지 않는다

수집에 잡힐 방화벽이 없으면 소스 모델의 `firewallTable` 이 비고, 거기서 나온 타깃 모델도 빈다. 규칙을 복제하는 시나리오는 전제가 무너진다. → `scripts/prepare-source-server.sh` 가 ufw 를 켠다.

### C-9. 돌리기 전에 환경이 살아 있는지 본다

개발 서버·소스 서버는 **저녁에 자동 종료**되고, 자동 종료 보류(`Auto.StopHold=keep`)는 **매일 06:00 에 풀린다** — 하루짜리다. 꺼진 환경에 시나리오를 걸면 스크립트 문제처럼 보이는 실패가 나고, 한 구간만 돌렸다면 타임아웃까지 기다린 뒤에야 알게 된다.

→ `scripts/check-env.sh` 를 먼저 돌린다. 콘솔 응답·컨테이너 healthy·**플랫폼 호스트에서** 소스 서버 SSH 도달·화면 식별자 존재를 한 번에 본다.

> 2026-07-29: 전날 19시에 세 대가 모두 내려간 상태에서 전체 실행을 걸어 전 구간이 2 초 만에 죽었다. DNS 도 함께 사라지는데(`Auto.Dns` 는 running 일 때만 등록된다) 그것을 확인하지 않았다.

### C-10. 검증 코드도 제품 코드만큼 의심한다

멀쩡한 것을 이상하다고 말하는 쪽이 검사기일 때가 많다. 같은 날 세 번 나왔다.

- 포트를 `Ports` 로 읽어 전부 `undefined` → *"5555 가 안 열렸다"* (실제로는 열려 있었다)
- 컨테이너 상태를 `" healthy"` 로 찾음 → 상태 문자열은 `(healthy)` 라 **23 개 전부 비정상**으로 셈
- `grep` 이 못 찾으면 1 로 끝나는데 그것을 실패로 봄 → 정상인데 판정 불가

→ 검사 결과가 이상하면 **제품보다 검사 명령을 먼저 의심한다**([[destructive_cmd_no_head_truncation]] 와 같은 취지).

### C-11. 규칙은 적어 두는 것으로 지켜지지 않는다 — **코드로 막는다**

§A 는 *"필수값이 비면 더미로 돌지 말고 즉시 실패시킨다"* 라고 2026-07-15 에 적었다. 그런데 코드에는 아무것도
없었다. 그래서 2026-07-29 에 같은 일이 그대로 일어났다 — 키 없이 돌려 더미 비밀번호로 등록됐고, 등록은
성공했으며, 수집에서 SSH 인증 실패가 났다. 그걸 보고 **파일 임포트가 깨졌다**고 판단해 멀쩡한 코드를 고쳤고,
그 다음엔 개별 등록까지 실패하는 걸 보고서야 원인이 내 실행 환경이라는 걸 알았다.

→ 지금은 `support/globalSetup.ts` 가 `--project=integration|scenario|live` 실행에서
`TEST_SOURCE_PRIVATE_KEY`·`TEST_SOURCE_NANO_IP`·`TEST_SOURCE_MICRO_IP` 가 없으면 **시작 자체를 막는다**.
더미로 도는 것이 맞는 실행이면 `E2E_ALLOW_DUMMY_SOURCE=1`.

**소스 서버에 들어가는 키는 정해져 있다** — 아무 pem 이나 되지 않는다. 어느 키이고 IP 가
무엇인지는 팀 내부 문서에 있고, 값은 `e2e.config` 에 적어 둔다(`docs/03-환경설정.md`).

```bash
cp e2e.config.example e2e.config      # TEST_SOURCE_* 를 채운다
```

키 내용을 한 줄로 넣기 어려우면 그 값만 명령줄에서 준다.

```bash
TEST_SOURCE_PRIVATE_KEY="$(cat <키 파일>)" npm run test:e2e
```

### C-12. CSV 개인키는 **줄바꿈을 그대로** 둔다

여러 줄 값은 따옴표로 감싸면 줄바꿈째로 한 칸에 들어간다 — 가이드 문서(`docs/guide/source-connection-bulk-import.md` §4)와
서버 파서(`api/internal/handler/tabular_import_test.go`)가 둘 다 그렇게 말한다.

줄바꿈을 `\n` 두 글자로 바꿔 넣으면 **서버가 되돌리지 않는다.** 키에 역슬래시와 n 이 그대로 남아 SSH 가 읽지
못하고, 등록은 조용히 성공한 뒤 연결만 `failed` 로 남는다.

**`connection_status` 를 근거로 삼지 말 것** — 개별 등록한 정상 연결도 `failed` 로 보인다. 임포트가 제대로
됐는지는 **수집이 되는지**로 판정한다(`POST /honeybee/source_group/{id}/import/infra` 가 서버 수를 돌려준다).

### C-13. 화면 이동은 **주소 로딩이 아니라 메뉴 클릭**

`page.goto()` 는 애플리케이션을 통째로 다시 띄운다. 화면이 한 번 하얗게 비었다가 셸이 다시 그려지므로,
녹화본이 단계마다 깜빡인다. 메뉴 클릭은 라우트 전환이라 셸이 그대로 있고 화면만 바뀐다 — 사람이 하는 것도 그쪽이다.

→ `support/navigate.ts` 의 `openScreen(page, menuId, path)` 를 쓴다. 콘솔이 아직 안 열린 상태(새 브라우저·로그인
직후)에서만 주소로 이동한다. 메뉴 식별자는 `data-testid="menu-{라우트이름}"`(`entities/menu/model/types.ts` 의 MENU_ID).

**메뉴에 있는 것과 라우트가 있는 것은 다르다.** `mciwls`·`pmkwls` 는 라우트지만 사이드바에 없다 —
`api/conf/menu.yaml` 에서 `workloads` 의 자식이라, Workloads 화면이 자기 옆에 다시 목록으로 그린다.
그래서 두 단계다: `openSubScreen(page, 'workloads', 'mciwls', path)`. 옆 목록 항목은 `data-testid="lsb-{라우트이름}"`.

주소를 그대로 여는 방식에서는 이 차이가 안 보였다(어느 쪽이든 그냥 열렸다). 메뉴로 바꾸자 **구간3 이후 일곱 구간이
연쇄로 무너졌다** — 화면 이동 방식을 바꿀 때는 `menu.yaml` 의 부모·자식을 먼저 본다.

### C-15. ★ 행은 **그 표 안에서** 찾는다 (2026-07-31)

`getByRole('row', { name })` 는 화면 *어디에 있든* 행이면 잡는다. 목록 밖에 같은 이름을 담은 요소가 하나라도 있으면 매칭이 둘이 되고, `.first()` 가 엉뚱한 쪽을 집는다.

```ts
// ✗ 화면 전체에서 찾는다
this.page.getByRole('row', { name: new RegExp(name) })

// ✓ 그 표 안에서만
this.groupTable.getByRole('row', { name: new RegExp(name) })
```

**증상이 원인과 멀리 떨어져 나타난다.** 소스 서비스 등록 모달을 닫은 직후, 표 아래(y≈759)에 27px짜리 요소가 같은 이름을 달고 있었다. 클릭은 *성공*하고 아무 일도 일어나지 않는다 → 다음 단계가 열리지 않은 상세의 탭을 15초 기다리다 시간 초과 → 실패 화면에는 **선택되지 않은 목록만** 남는다. 그 화면만 보면 "왜 선택이 안 됐지"밖에 알 수 없다.

세 번을 다른 가정으로 다시 돌린 뒤에야 **매칭 개수를 찍어 보고** 알았다. 선택이 안 되는 것 같으면 먼저 `count()` 를 찍는다 — `E2E_DEBUG_SELECT=1` 로 켜 둔 로그가 그것이다.

### C-16. ★ 값을 *모양*으로 찾지 말고 *경로*로 찾는다 (2026-07-31)

워크플로우 본문에서 스펙을 고치려고 "`provider+region+size` 모양인 필드"를 찾았다. 먼저 걸린 것은 `targetSpecList[0].id` — **추천 후보 카탈로그**라 인스턴스 생성에 쓰이지 않는다. 정작 장비를 정하는 `targetInfra.nodeGroups[].specId` 는 그대로였다.

그런데 **검사는 통과했다.** 판정이 "파라미터 어딘가에 그 문자열이 보이는가" 였기 때문이다. 방금 자기가 타이핑해 넣은 칸을 보고 통과한 것이다. 그 결과 "워크플로우에서 바꾼 스펙이 인스턴스까지 반영됐다"는 **틀린 검증 결과를 보고**했다.

- 고칠 대상도 판정도 **경로**로 지정한다 (`[data-testid$="specId"][data-testid*="nodeGroups"]`).
- 못 찾으면 비슷한 것으로 갈아타지 말고 **실패**시킨다.
- 값을 쓴 쪽과 읽는 쪽이 같은 칸이면 그 검사는 아무것도 증명하지 않는다.

### C-17. 워크플로우 편집기는 **중첩 배열을 그리지 않는다** (2026-07-31)

객체 배열 안의 객체 배열이 펼쳐지지 않아, request body 에 분명히 있는데도 화면에 칸이 없다.

| 그린다 | 안 그린다 |
|---|---|
| `targetInfra.name` 등 | **`targetInfra.nodeGroups[]`** — specId·imageId·sshKeyId |
| `targetSecurityGroupList[0].name` 등 | **`targetSecurityGroupList[0].firewallRules[]`** — 포트 |

편집기에서 스펙이나 방화벽 포트를 바꾸는 시나리오는 **디자이너로는 성립하지 않는다.** Run Status 의 **View JSON** 으로 원본을 고쳐 저장하는 길을 쓴다.

무엇이 그려지는지는 `specs/body-fields-dump.spec.ts` 가 전부 출력한다(실측 373개).

### C-18. ★ 인프라가 "생겼다"는 것은 레코드가 아니라 **노드**로 판정한다 (2026-07-31)

인프라 생성을 기다리는 로직이 `ListInfra` 에서 접두어가 맞는 항목을 찾으면 "만들어졌다"고 판단했다. **VM 이 하나도 뜨지 않았는데도** 인프라 레코드는 남으므로, 실패한 생성을 성공으로 읽는다.

실제로 그랬다 — AWS 가 그 가용영역에 t3a.medium 용량이 없어 `all 1 VMs failed to create` 로 끝났는데, 대기 로직은 `t1-…-infra101` 을 찾아 다음 단계로 넘어갔다. 잡아낸 것은 **작업별 상태 검사**였다(`infra_migration = Failed`).

- 기다릴 때 노드 수와 상태까지 본다. 레코드만으로는 아무것도 증명하지 못한다.
- **워크플로우 전체 상태는 여전히 `success` 다.** 마지막 통지 작업이 `trigger_rule: all_done` 이라 앞이 실패해도 초록으로 끝난다(§B-2와 같은 이야기). 작업별 상태 검사를 지우지 말 것.

> AWS 용량 부족(`InsufficientInstanceCapacity`)은 우리 환경 문제가 아니고 대개 일시적이다. 다만 *어느 스펙이 부족한지*는 갈린다 — 같은 시각에 t3a.medium 은 못 뜨고 t3a.large 는 떴다.

### C-19. ★ 촬영 중에는 다른 playwright 를 돌리지 않는다 (2026-08-01)

playwright 는 실행을 시작할 때 `test-results` 를 **통째로 비운다.** 촬영이 도는 중에 확인용 spec 하나를 돌렸더니 그 폴더가 지워졌고, 그때 찍히던 구간의 영상이 통째로 날아갔다.

- 시나리오는 **정상적으로 끝났다.** 인프라도 제대로 만들어졌다. 없어진 것은 영상뿐이라, 로그만 보면 무엇이 잘못됐는지 알기 어렵다(`ENOENT … .playwright-artifacts-0/traces/…`).
- 그 구간이 모델을 만드는 자리면 같은 이름표로 다시 찍을 수 없어 **한 벌을 통째로 다시** 찍어야 한다.

→ `scripts/record-all.sh` 가 자물쇠를 잡는다. 촬영 중 다른 실행은 거부된다. 확인용 spec 은 촬영이 끝난 뒤에 돌린다.

### C-20. ★ "이미 선택돼 있다"는 **행의 표시가 아니라 상세가 열렸는지**로 본다 (2026-08-01)

선택된 행을 다시 누르면 선택이 풀리고 그 아래 상세도 같이 닫힌다. 그래서 "이미 선택돼 있으면 건너뛴다"를 넣었는데, 판정 근거를 *행에 붙은 selected 클래스*로 삼은 것이 문제였다.

- 행은 선택 표시를 단 채로 **상세는 닫혀 있을 수 있다.** 그러면 클릭을 건너뛰고, 다음 단계가 기다리는 탭은 영영 나오지 않는다.
- 클릭에는 시한이 없다. 그래서 **실패하지 않고 그 자리에 서 있는다** — 43분을 서 있다가 테스트 전체 시한에서야 끝났다. 로그 마지막 줄은 그 앞 단계의 정상 출력이라 원인이 보이지 않는다.

→ 판정은 **연결 탭이 실제로 보이는지**로 한다. 그리고 탭을 누르기 전에 `toBeVisible({ timeout })` 을 하나 둔다 — 없는 것을 누르려 할 때 *멈추는 대신 실패하게* 만드는 장치다.

### C-21. ★ DAG 가 등록되지 않으면 **기다림을 늘리지 말고 airflow 부터 본다** (2026-08-01)

워크플로우를 저장하면 DAG 파일이 만들어지고, airflow 의 dag-processor 가 그것을 읽어 가야 실행할 수 있다. 읽어 가기 전에 실행하면 거부된다.

그날 이 대기가 3분에 걸려 실패했다. 시한이 짧은 줄 알고 6분으로 늘렸더니 **6분도 넘겼다.** 늘릴수록 한 구간에 정지 화면만 길게 쌓였다.

원인은 대기가 아니었다. **airflow-server 안에서 `scheduler` 와 `dag-processor` 가 죽어 있었다** — 전날 디스크가 가득 차 mysql 이 내려갔을 때 함께 죽은 뒤 돌아오지 않았다. 컨테이너는 `healthy` 였고(살아 있는 api-server 가 응답한다), 이미 등록돼 있던 DAG 는 잘 돌았다. **새 DAG 만 영영 등록되지 않았다.**

확인은 컨테이너 안의 프로세스를 세는 것으로 한다. `ps` 가 없으므로 `/proc` 을 읽는다:

```bash
docker exec airflow-server bash -c 'for p in /proc/[0-9]*; do tr "\0" " " < $p/cmdline; echo; done' \
  | grep -oE "airflow (scheduler|dag-processor|api_server)" | sort -u
```

셋이 다 나와야 한다. `api_server` 만 있으면 그 상태다. 되살리는 것은 컨테이너를 다시 띄우면 된다(raw docker 말고 mayfly 로):

```bash
./mayfly infra stop -s airflow-server && ./mayfly infra run -d -s airflow-server
```

되살린 뒤에는 밀려 있던 DAG 가 **바로** 등록된다. 몇 분씩 기다릴 일이 아니다.
